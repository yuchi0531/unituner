# unituner POLICY

> **unituner は「チューナー共有」だけに焦点を置いたソフトウェアである。**
> 機能の広さではなく、**高速**で、**堅牢**で、**安定**していることを目標とする。
> さらに**非力な STB や市販ネットワークチューナー（armv7 / aarch64）への移植**を前提に、
> 少ないメモリと CPU で動くことを設計条件に含める。
> そして**標準仕様にのみ対応し、特殊ケースは pipeline 側で吸収する**。
>
> 実装の詳細は [SPEC.md](SPEC.md)、実機手順は [TESTING.md](TESTING.md)。
> SPEC と衝突したら実装については SPEC が正、新しい要求をどう扱うかについては本書が正。

## 0. 目的と優先順位

unituner が解く問題は 1 つだけ。

> 複数のクライアントが、限られたチューナーを、取り合い・待ち・奪取で壊さず共有できるようにする。

評価軸は機能数ではなく、次の順序で固定する。

1. **正しさ** — 選局・共有・奪取・解放が仕様どおりに動く
2. **高速** — 共有のための追加コピー・追加待ち・追加プロセスを作らない
3. **堅牢** — 不正入力・異常終了・切断で落ちない、資源を残さない
4. **安定** — 長期稼働と反復操作で挙動が変わらない
5. **軽さ** — 非力なハードウェア（armv7、1 コア、数百 MB の RAM）でも実用になる
6. **機能** — 上記を悪化させない範囲でのみ足す

**新機能は、この 1〜5 を悪化させないことを条件に許可する。** 便利さのためにホットパスを複雑にする提案は、まず pipeline か外部ツールで解けないかを検討する。

### 標準仕様のみ（特殊ケースは pipeline へ）

これは他のすべての判断に優先する前提である。

- **本体が実装するのは標準仕様だけ**: MPEG-2 TS（ISO/IEC 13818-1、188 バイト。対象チューナーが普通に出す 204 はパリティを落として受ける）、ARIB STD-B10 の SI（PAT / PMT / SDT / NIT）、ARIB STD-B24 の文字、mirakurun 互換 HTTP API のサブセット。
- **上記に無いものは本体に入れない**。192 バイトフレーミング、TLV/MMT、ベンダー固有のスクランブルやリマックス、非標準の PAT/PMT 配置、機器固有のチャンネル番号体系、特殊な API 方言などは、pipeline の外部コマンド・設定・別ツールで吸収する。
- **標準外を検出したら黙って解釈しない**。捨ててカウントするか、明示的なエラーにする。誤解釈してゴミを配信するより、扱えないと明示する方が堅牢である。
- **ベンダー名・機種名で分岐するコードを書かない**。設定で表現できないなら pipeline の仕事である。
- 標準の解釈に幅がある箇所（204 の RS パリティ、複数セクションの SDT、`current_next_indicator` 等）は、**標準が要求する範囲だけ**面倒を見る。標準にない救済措置を本体に足さない。
- これは高速・堅牢・移植性のための制約でもある。分岐と例外処理を増やすほど、ホットパスが遅くなり、バグと移植の穴が増える。

## 1. スコープ（チューナー共有だけ）

やる:

- 外部コマンドチューナーの共有・排他・奪取（`(type, channel)` 単位の 1 本のプロセス木）
- mirakurun 互換 API のサブセット（`/api/version` 〜 `/api/tuners`、ストリーム 3 種）
- 内蔵サービスフィルタ（service stream の PAT 書き換え + PID 絞り込み）
- チャンネル探索 API（curl で叩く）とサービス表（永続キャッシュ + 手動 Re-scan）
- 管理 web UI（設定の閲覧・編集と再起動）

やらない:

- EPG、録画、タイムシフト、ロゴ（CDT）、番組情報
- MMT/TLV の内部処理、B-CAS / B25 / C-CAS の内蔵デコード
- 永続 DB、hot reload、認証、マルチノード

**追加要求の第一基準**: それは「チューナー共有の正しさ・速さ・丈夫さ・安定・軽さ」に効くか。かつ**標準仕様の範囲か**。
標準外なら、本体ではなく pipeline の外部コマンド・設定・別ツールで解く。共有に効かなければ unituner の仕事ではない。

例外は例外として明示する。`decode=0` が生 TLV を流すのは TS-only 原則の**許容済み例外**であり、黙って隠さず README と SPEC の制限欄に書く。

## 2. 高速（fast）

**共有のためのオーバーヘッドをゼロに近づける。** チューナーが運ぶビットレートに対して、unituner は「通過させるだけ」であるべき。

- **ホットパスは 1 パケットあたりヒープ割り当てゼロ**。`tsframe` / `tsfilter` は同期・バッファ再利用で、パケットごとに `Vec` を作らない。
- **コピーは必要な箇所だけ**。188 整列済みの入力はスライス上でそのまま処理する。コピーが発生してよいのはチャンク境界の詰め替えだけ。
- **PID 判定は O(1)**。8192 bit のビットマップで通過判定し、パケットごとの線形探索をしない。PAT/PMT が PID 集合を変えたときだけ再構築する。
- **待ちはイベント駆動**。セッション状態の変化・spawn 完了・shutdown は `Notify` で起きる。固定間隔のポーリングで遅延や CPU を足さない。
- **channel stream は追加コピーなし**。共通 broadcast の `Bytes` をそのまま配信する。購読者ごとの処理は service stream のフィルタだけに限定する。
- **1 セッション 1 プロセス木、同一 `(type, channel)` は相乗り**。同じチャンネルの 2 人目にチューナー起動コストを払わせない。これがこのソフトウェアの存在理由そのもの。
- **スキャンは並列**、待機はイベント駆動。起動時は `services.json` が有効なら**チューナーに触らずスキップ**する。
- **ログをホットパスで吐かない**。per-packet / per-chunk のログは debug でも既定で出さない。
- **チャンクは 188 の倍数**、既定 64 KiB。極端に小さい値はスループットとスキャン正当性を壊すため、妥当な範囲を検証で守る。
- **計測してから最適化する**。性能変更は before/after を数字で示す。感覚で最適化しない。

**目標値**（設計上の下限として扱う）:

- フル TS（約 17 Mbps / 2.1 MB/s）の配信で、unituner 自身の CPU 使用率が無視できる範囲（64-bit 機で 1 コアの数 %、armv7 でも 1 コアで余裕を残す）。
- 選局から最初のバイトまでの**追加**遅延が 1 チャンク以内（既定 64 KiB ≒ 30 ms）。支配要因はチューナー起動時間であり、unituner がそこに更なる待ちを足さない。
- 2 人目以降の同時視聴で、追加のプロセス起動・追加のコピー・追加の遅延が発生しない。

## 3. 堅牢（robust）

**壊れた入力で落ちない。落ちるときは設定時に落ちる。**

- **不正な TS / SI / HTTP / YAML で panic しない**。`unwrap` / `expect` はテストと起動時不変条件に限定する。壊れたパケットは捨ててカウントし、ストリームは継続する。
- **起動時に fail-fast、実行時に全体を落とさない**。設定エラーは起動時にファイル名・項目付きで報告する。1 チャンネルの異常や 1 セッションの失敗でサーバ全体を止めない。
- **すべての外部プロセスに timeout、すべての待ちに上限**。readiness、scan、停止猶予、shutdown に無期限の待機を置かない。
- **キャンセル安全**。HTTP の切断、タブ閉じ、scan のタイムアウトで `Starting` 予約・プロセス木・デバイスを残さない（Drop ガード / detached spawn + oneshot）。
- **エラーは分類して握り潰さない**。`no signal` / `tuner failed to start` / `busy` / `preempted` / `no tuner for type` / decode 競合を区別し、展開後の argv 付きで理由を出す。
- **設定外のチャンネルはチューナーを起こさない**（404）。`channels.yml` は資源の allowlist であり、飾りではない。
- **静的に決まるエラーは GET と HEAD で一致**。HEAD が 200 を返して GET が 503 になる、という嘘をつかない。
- **停止は確実**。setsid したプロセスグループへ SIGTERM → 猶予 → SIGKILL。SIGTERM / SIGINT で全セッションを止め、子プロセスを残留させない。
- **失敗時は巻き戻す**。部分的な spawn 失敗で「登録済みだが出力なし」のセッションを残さない。奪取の spawn 失敗で victim を道連れにしない。

## 4. 安定（stable）

**同じ操作を繰り返しても、長時間動かしても、挙動と資源が変わらない。**

- **リークしない**: 子プロセス、fd、スレッド、メモリ、セッション予約、購読者枠。反復操作の後に増えていないことをテストで確認する。
- **上限は 4 層**: per-session / per-IP / 全体セッション数 / 合計バイト。すべて bounded で、超過は 429。無制限のキュー・無制限の購読者を作らない。
- **バックプレッシャを設計に入れる**。購読者が遅いときに無制限にバッファせず、追い越したら lag として落とす。メモリは最悪ケースの予約として上限を持つ。
- **奪取の thrash を抑える**。priority 128 同士の ping-pong、連鎖 evict で高優先度セッションが不安定になる挙動は、cooldown か FCFS で抑制する。
- **リトライは一時的なものだけ**。busy / preempted は backoff、起動失敗はリトライしない。無限リトライでログと CPU を焼かない。
- **状態は決定的**。同じ設定と同じ `services.json` で再起動したら同じ結果になる。起動順・並列スキャン順に依存する結果を作らない。
- **キャッシュは追記的に育たない**。サービス表は upsert、設定から消えたチャンネルだけ落とす。放送再編は手動 Re-scan。
- **アイドルで解放する**。最後の購読者が抜けたら `idle_timeout` 後にプロセス木を止める。チューナーを遊ばせたまま保持しない。
- **長期稼働で検証する**。連続視聴・zapping・同時接続・Re-scan の反復で、RSS と fd が単調増加しないことを実機 soak で確認する。

## 5. 移植性と低資源（armv7 / 非力な STB）

**「動く環境を選ばない」ことも機能のうち。** 市販ネットワークチューナーや古い STB は、1 コア・数百 MB の RAM・32-bit ARM であることが珍しくない。ここで動かない設計は採用しない。

- **ターゲット**: `armv7-unknown-linux-{gnueabihf,musleabihf}`、`aarch64-unknown-linux-{gnu,musl}`、`x86_64-unknown-linux-{gnu,musl}`。Linux を前提とする（`setsid` / `killpg` を `libc` で直接使うため）。
- **単一バイナリ・外部依存なし**。フロントエンドのビルド工程も、別デーモンも、DB も要らない。配布は musl 静的リンクを選択肢に持つ（glibc の版差で動かない環境を避ける）。
- **依存を増やさない**。新しいクレートはバイナリサイズ・ビルド時間・メモリのコストとして説明する。重い抽象化（非同期ランタイムの多重化、汎用プラグイン機構など）を安易に持ち込まない。
- **常駐メモリを小さく保つ**。目標はアイドル時（セッション 0）で 1 桁 MB 台。超えたら原因（バッファ、スレッド、キャッシュ）を調べる。購読者バッファは最悪ケースの予約ではなく、実際に積まれた分だけがメモリになる。
- **スレッドを増やさない**。セッションごと・購読者ごとに OS スレッドを作らない。 tokio タスクで多重化する。非力な環境向けに runtime の worker 数を絞れるようにする（現状は既定でコア数に従う。移植時に必要なら設定項目を追加する）。
- **32-bit を壊さない**。`usize` は 32 bit である前提で書く。配列長・オフセットの計算で暗黙の 64 bit 前提を持ち込まない。エンディアン依存の読み書きをしない。unaligned アクセスを前提にしない。
- **32-bit のアドレス空間を尊重する**。`max_subscriber_buffer_bytes` の既定 2 GiB は 64-bit 前提の値である。armv7 のような 32-bit 環境では、実メモリとアドレス空間に合わせた既定（例: 256–512 MiB）に落とす。同じ既定値を全ターゲットに押し付けない。
- **CPU 機能に依存しない**。SIMD / x86 専用命令を必須にしない。あっても「あれば速い」任意経路とし、スカラー経路が常に正しい。
- **時刻は単調時計**。`Instant` を使い、壁時計の飛び（NTP、手動変更）でタイムアウトや idle 判定が壊れないようにする。
- **クロスビルドを壊さない**。armv7 / aarch64 のビルドを定期的に通す。実行確認は qemu か実機で行い、x86_64 だけで「動く」と判断しない。
- **実機の数字で語る**。armv7 実機でフル TS 配信時の CPU / RSS / スループットを測る。測定できない環境では、少なくともクロスビルドと起動・1 ストリームのスモークを通す。
- 移植性を理由に**機能を削らない**。削るのではなく、重い実装を避ける。

## 6. 互換性

- **互換は API 形状の互換であって、身元の詐称ではない。**
  `Server: unituner/<version>`、`/api/version` は `current == latest`、レスポンスボディに `Mirakurun` を出さない（mirakc と同じ正直な自己識別）。
- ただし**ワイヤプロトコルの識別子は残す**。`X-Mirakurun-Tuner-User-ID` / `X-Mirakurun-Priority` / `X-Mirakurun-Tuner` は「相手がそう呼ぶから」であって、自己紹介ではない。
- **互換の判定は実クライアント**。EPGStation、BonDriver_Mirakurun、KonomiTV が動くことが基準。
  - 例: `Host` が無い/空の要求を 403 にしないのは BonDriver_Mirakurun がそう送るため。`Host` が存在して許可外なら 403（DNS リバインディング対策は維持）。
- **互換仕様はソースで確認する**。mirakc / mirakc-BS4K / Hotarun / mirakurun 本家のコードを読み、記憶や推測で決めない。
  - 例: 奪取条件は「victim の**最大** priority より真に大きい」。最小 priority を見ると高優先度ユーザーを巻き込むので誤り。
- **拡張は既定で無効**。`routes` 未指定・pinning 未指定・pipeline 未指定は、すべて従来挙動に落ちる。新機能を足すときは「書かなければ今までどおり」を必ず保証する。
- 差分は制限として書く。mirakc-BS4K の `X-Mirakc-Tuner` を service stream にも広げたこと、`X-Mirakurun-Tuner` alias を足したこと等は README に明記する。

## 7. 責務の境界（TS-only 原則）

- **unituner が解釈するのは MPEG-TS だけ**。SI 解析、フィルタ、配信はすべて 188 バイトパケット前提。扱う形式を 1 つに絞ることが、高速・堅牢・移植性の前提でもある。188 / 204 以外のフレーミング（192 バイト等）は pipeline で正規化する。本体は検出して拒否するだけである。
- **pipeline はチューナー出力を byte-for-byte で受け、必ず TS を出力する。**
  TLV/MMT → TS 変換、デスクランブル、不要 PID 除去、再パケット化は pipeline の責務。重い処理は本体の外に置く。
- **204→188 正規化は pipeline の後段に 1 箇所だけ**。pump が最終段の出力に適用してから broadcast する。
  入力側で正規化しない。TLV に `0x47` を探してストリームを壊すのが、BS4K が `no signal` になった実因だった。
- **入力フレーミングを設定で宣言しない**。`input: ts|tlv` のような項目は廃止した。
  設定を増やすより「pipeline は何を受けても TS を出す」という 1 つの契約で吸収する。
- **`decode=0` は pipeline 全段バイパス + 正規化なし**。生バイトをそのまま返す。
  TLV 源では TS ではなく TLV が流れる。これは許容済み例外として明示する（上記）。
- 外部 B25 デコーダの例は **`arib-b25-stream-test`** と表記する。デスクランブル実装の固有名をドキュメントに出さない（実装は差し替え可能な部品として扱う）。

## 8. 設定

- YAML 4 分割（`server` / `tuners` / `channels` / `pipelines`）+ 生成物 `services.json`（手編集しない）。
- **起動時 fail-fast**。問題はファイル名と該当項目付きで報告し、非 0 で落ちる。
- **未知フィールドは拒否**（`cmd:` のような typo を黙って無視しない）。
- **意味レベルの検証**を行う。型の正規表現は 3 ファイル横断で適用、参照先の存在、空 command の拒否、`scan > readiness` の順序、チャンクサイズの妥当範囲。
- **webui の保存も起動時と同じ検証を通す**。UI から壊れた設定を書けない。
- **保存は原子的**: `.bak` → tmp 書き込み → fsync → rename。失敗時は書き戻さない。パーミッションは 0600 / 既存 mode を維持。
- **既定値は「運用に耐える」を優先**し、資源上限はテストでピン留めする。
  - 例: 購読者バッファ予算 256 MiB は同時 4 人で上限に達したので **2 GiB**（= 32 購読者 × 64 MiB）へ。ただしこれは 64-bit の既定であり、32-bit ターゲットでは §5 の通り下げる。
- **設定を増やす前に 3 回考える**: 既定で吸収できないか、pipeline で解決できないか、実行時引数で足りないか。
  増やすなら「検証 + README 記載 + テスト」を同じ変更にセットで入れる。
- **子プロセスの環境は継承しない**。`PATH` / `HOME` / `TMPDIR` / cwd を明示する。
  サービス実行と手動実行で `dtv.names` の探索先が変わる、といった差で壊れないため。

## 9. 状態とキャッシュ

- **起動のたびに全チャンネルを舐めない**。`services.json` を読み、fingerprint が一致すればチューナーに触らず即座に配信可能にする。これは起動時間・無駄なチューナー占有・非力な CPU のすべてに効く。
- **fingerprint は「放送の性質を変える設定」だけ**。enabled な `channels.yml` の `(type, channel, extra-args, routes)`。`disabled` は除外、`tuners.yml` は含めない。
- **キャッシュは無期限**。放送再編は手動 Re-scan で追随する。期限付き自動更新は YAGNI。
- **更新は upsert のみ**。busy / 無信号のチャンネルは既存レコードを保持し、設定から消えたチャンネルだけフルパス完了後に落とす。
- **中途半端に書かない**。クライアント切断・shutdown 時は retain もキャッシュ書込も行わない。

## 10. API と UI の分け方

- mirakurun 互換は `/api/*`。独自機能は `/webui/api/*` に閉じる。互換名前空間を独自用途で汚さない。
- **チャンネル探索は curl 用**（`PUT /api/config/channels/scan`）。webui には出さない。
- **webui の Re-scan はサービス表専用**で `channels.yml` を書かない。探索と混同しないよう別ボタン・別ダイアログにする。
- **webui はルート配信**（`host:port/`）。`/web` のような脇道を作らない。
- 見た目は Material Design 2。**ダーク既定 + トグル**（localStorage、未保存時は OS 設定に追従、描画前適用でちらつきなし）。Restart はヘッダー内、Channels は型別サブタブ、Services は物理 ch 列。
- webui は認証なし。**`allowed_cidrs` / `allowed_hosts` が境界**であり、LAN 内前提であることを README に書く。
- webui はチューナー共有の本筋ではない。**UI の都合でバックエンドのホットパスや状態モデルを変えない。** 埋め込みアセットは非力な環境でも配れる大きさに保つ。

## 11. 検証

- **実機で確かめる**。PX-S1UD + recisdb。ドロップは仕様であり、それ自体を不具合として扱わない。
- fake チューナー（`cat` / `head -c` / `sleep` / 存在しないコマンド）で回帰を固定する。実機が無い日でも壊れたことが分かるように。
- 変更時の最低ライン: `cargo test` / `cargo clippy -D warnings` / `cargo fmt --check`。
- **クロスビルド**を定期的に通す（armv7 / aarch64）。少なくとも起動・`/api/version`・1 ストリームのスモークを qemu か実機で行う。
- 高速性の確認: ホットパスに割り当てが増えていないこと、待ちがポーリングになっていないこと、2 人目の視聴でプロセスが増えないこと。
- 堅牢性の確認: 壊れた TS / 途中で死ぬチューナー / 即座に切断するクライアント / 不正な設定での起動。
- 安定性の確認: zapping と同時接続の反復、アイドル解放、shutdown 後の子プロセス・fd 残留なし。
- 軽さの確認: アイドル時 RSS、フル TS 配信時の CPU、armv7 実機でのスループット。
- 実機で見るもの: 188 整列、先頭 `0x47`、tuner の解放、スキャン結果の一致、`services.json` の更新。
- **主張はコードで確認する**。ユーザーの指摘が正しいか分からないときは、同意も反論もせずにまずコードを読み、再現し、修正余地があれば直す。
- テストは「通った」だけでは不十分。クリティカルな経路は実機相当の end-to-end で 1 回通す。

## 12. 進め方

- 大きな変更は**ファイルが重ならない単位に分割して並列に進め**、最後に統合して全体テストを回す。
- 優先順は「動かして壊れる層」→「結果の正しさ」→「速度・資源・安全性」→「保守性」。
- コミットは小さく、コード + テスト + docs（SPEC / README）を同じ変更に含める。
- **push は指示があるまでしない**。リポジトリは private。
- ドキュメントは日本語。コマンド・識別子・ログは原文のまま。

## 13. 判断に迷ったときの順序

1. **チューナー共有に効くか**（このソフトウェアの存在理由か）
2. **標準仕様の範囲か**（特殊ケースなら pipeline で解けるか）
3. **実クライアントは動くか**（互換の実測）
4. **高速性を悪化させないか**（割り当て・コピー・待ち・プロセス起動）
5. **壊れた入力や切断で落ちないか**（堅牢）
6. **繰り返し・長期稼働で資源が増えないか**（安定）
7. **非力な環境（armv7 / 1 コア / 小メモリ）で動くか**（軽さ）
8. **設定を増やさず既定で吸収できないか**
9. **失敗したとき原因が分かるか**
10. **制限としてドキュメントに書けるか**（隠さず書けるなら許容、書けないなら設計が悪い）

## 14. アンチパターン（やってはいけない）

- チューナー共有と無関係な機能を本体に足す（EPG・録画・デコード内蔵・DB）
- 互換のために `Mirakurun` と名乗る（身元の詐称）
- pipeline の入力側で 204→188 正規化する（TLV を壊す）
- ホットパスでパケットごとに `Vec` を確保する / パケットごとにログを出す
- 同じチャンネルの 2 人目に新しいプロセスを起動する（相乗りを壊す）
- 固定間隔のポーリングで状態変化を待つ（遅延と CPU を無駄に使う）
- 無制限バッファ・無制限購読者（OOM と DoS の入口）
- 取得のキャンセルで `Starting` 予約を残す（チューナー恒久占有）
- 「チューナー起動失敗」を `no signal` に丸める（原因が見えなくなる）
- 設定に無いチャンネルでチューナーを起動する（allowlist の無効化）
- HEAD で楽観的な 200 を返す（クライアントの事前判定を壊す）
- 暗黙のフォールバック（pinning / routes で指定した以外へ勝手に流れる）
- 無限リトライ / 無期限の待機
- webui に探索とサービス再スキャンを混ぜる（`channels.yml` の二重書き込み）
- 64-bit / x86 前提をコードに埋め込む（armv7 で動かなくなる）
- 32-bit 環境に 2 GiB の既定予算をそのまま持ち込む（アドレス空間を食い潰す）
- セッションごと・購読者ごとに OS スレッドを立てる（非力な環境で破綻する）
- 重い依存や汎用プラグイン機構を「便利そう」で足す（バイナリとメモリが膨らむ）
- 標準外のフレーミング・ベンダー固有の癖を本体で吸収する（pipeline の仕事）
- ベンダー名・機種名で分岐する（設定か pipeline で表現する。本体にifを増やさない）
- テストが緑だからと実機を見ない（ドロップ・遅延・権限は実機でしか出ない）

## 15. 主な決定と根拠（記録）

| 決定 | 根拠 |
|---|---|
| `Server: unituner/<version>`、`/api/version` は current == latest | 互換でも身元を偽らない。mirakc が同じ方式で実用上動いている |
| `Host` 空は許可、存在して許可外は 403 | BonDriver_Mirakurun が Host を送らない。ブラウザは authority 必須なので rebinding 対策は弱まらない |
| 204→188 正規化は pipeline 後段のみ | 入力側で正規化すると TLV を TS と誤認して破壊する（BS4K の no signal の実因） |
| `input`（`ts` / `tlv`）を廃止 | unituner は TS のみ扱う。TLV→TS は pipeline の契約で吸収する |
| 購読者バッファ既定 2 GiB（64-bit） | 256 MiB は同時 4 人で上限に達した。既定で運用を詰まらせない。32-bit では下げる |
| `services.json` + fingerprint、無期限 | 起動のたびの全 ch スキャンは無駄で遅い。放送再編は手動 Re-scan |
| チャンネル探索は curl、サービス Re-scan は webui | 探索は `channels.yml` を書き、Re-scan は `services.json` を書く。別物を混ぜない |
| `routes` 未指定は従来挙動 | 新機能は「書かなければ今までどおり」を守る |
| `passthrough` 疑似コマンド | 生 TS 運用を設定で表現できる。空 pipeline を特別扱いしない |
| 子プロセスの環境を固定 | サービス実行と手動実行の差（PATH/HOME）で外部コマンドが壊れる |
| readiness 30 秒 / scan 60 秒 | tune 6–11 秒 + デスクランブラ初回 9–15 秒の実測に合わせる |
| Linux / armv7・aarch64 を第一級ターゲット | 移植先は STB・市販ネットワークチューナー。単一バイナリ・低メモリで動く必要がある |
| 標準仕様のみ対応、特殊ケースは pipeline | 本体の分岐を増やさないことが高速・堅牢・移植性の前提。ベンダー固有の癖は設定で表現するか外部コマンドで吸収する |
